## 0. 结论与优先级

当前分数结构是资源 30 + 对抗 15 + 任务 15。现有清单已经覆盖了“规则机制缺口”和“资源路线”；本文补充的是更偏**建模、风险和时间分配**的方向，不是再加一个局部权重。

| 新方向 | 价值 | 成本/风险 | 建议 |
| --- | --- | --- | --- |
| 1. 对手下一 Tick 信念分布 | 中高 | 中 | 中期 |
| 2. 时间展开滚动规划 | 高 | 高 | 长期，不建议比赛前大改 |
| 3. 死亡的真实机会成本 | 中高 | 低中 | 优先验证 |
| 4. 对手资源意图与后期剥夺 | 中高 | 中 | 优先用日志验证 |
| 5. 全局分数预算/动态风险 | 中高 | 中 | 中期 |
| 6. 裁判端机制预言机 + 对手联盟 | 高（认知收益） | 低代码 | 立刻可做 |

如果时间有限，建议顺序：**6 → 3 → 4 → 1/5 → 2**。  
如果只能选一个“新策略”，建议先做 **3 + 4 的组合**：用真实死亡成本决定“值不值得冒险”，用对手资源意图决定“抢还是让”。

## 1. 对手从“单点位置”升级为“下一 Tick 信念分布”

### 当前实现

- `World.enemies` 只保存最后观察位置和 Tick（`core.cpp:236-283`）。
- `tactical_forecast` 只从连续两帧估计一个速度和一个预测点（`core.cpp:392-464`），默认关闭。
- 威胁计算和射击位置基本使用当前点或单点预测（`core.cpp:1077-1149`）。
- `safe_progress_moves` 会枚举敌人“停留 + 四邻”，但只是硬集合，没有概率权重（`core.cpp:1183-1238`）。

### 新思路

对每个可见敌人维护一个**下一 Tick 的离散分布**：

- 可能位置 = 停留 + 四个合法邻格；
- 排除已知墙、当前占位；
- 根据最近移动方向、是否刚防御、HP、是否保护加权；
- 未知格仍按可通行假设，不写成地图事实。

用途：

- **下一 Tick 受火风险**：不是“敌人现在是否瞄准我”，而是“下一 Tick 敌人有多大可能出现在能打到我的格”；
- **资源竞争**：估计敌人到资源的到达时间分布，而不是单点 BFS；
- **辣椒/堡垒**：估计敌人下一 Tick 是否还在火线/堡垒区；
- **撤退/推进选格**：避免走到“当前安全、下一 Tick 高暴露”的格子。

**边界**：本 Tick 的攻击在移动前结算，所以当前攻击仍用敌人当前坐标；信念分布主要改善下一 Tick 防御、路线和资源竞争，不能用来预测本 Tick 已结算的攻击。

### 为什么值得做

当前 `tactical_forecast` / `safe_progress_moves` 已经有“可能性”的雏形，但一个是单点，一个是硬集合。概率化后可以把“敌方可能动作”统一到防御、资源、事件风险里。

### 验证

- 无事件四车配对，比较死亡次数、D、资源、名次；
- 不要只看“预测更准”，要看最终指标；
- 与当前 `tactical_forecast` 默认关闭的基线分开统计。

## 2. 时间展开的滚动规划

### 当前实现

- 静态 Dijkstra 计算到达成本（`core.cpp:476-498`）；
- 目标用 `reward / cost^0.85` 打分（`core.cpp:499-847`）；
- 动作层再做一步战斗/事件估值（`core.cpp:1239-1550`）；
- `event_escape` 只对事件做了时间层反推（`core.cpp:396-435`），没有把敌人、资源、战斗放进同一时域。

### 新思路

做 8–16 Tick 的时间展开图：

- 节点 `(cell, tick)`；
- 边：move、wait、defend、attack；
- 成本/收益：已知事件伤害、敌人信念分布下的受火风险、资源/任务到达收益、死亡机会成本；
- 只执行第一步，下一 Tick 重规划。

这相当于把现在的“资源路线、事件逃生、局部战斗”统一成一个小的滚动优化问题。

### 为什么值得做

当前很多决策是“本 Tick 看起来好，但两 Tick 后没有退路”。时间展开能直接表达“先进去拿资源、再留一个出口”的时序，而不是靠多个惩罚项拼接。

### 风险与建议

复杂度高，容易把现有默认行为改乱。建议先只做**移动 + 资源 + 已知事件**，不加战斗；验证稳定后再加敌人信念。比赛前不建议大改。

## 3. 死亡的真实机会成本

### 当前实现

- `projected_damage` 只按死亡扣 60（`core.cpp:53-55`）；
- `damage_reserve` 是固定 120（`core.cpp:1408-1428`）；
- `respawn_task_route` 和 `survival_conditioned_progress` 只覆盖特定任务路线/存活分支，已证明没有整体收益（`core.cpp:848-882`、`1404-1407`）。

### 新思路

计算一个更完整的“生命价值”：

```text
death_cost ≈ 60 D 的分数损失（接近 500 时约 1.8 分）
           + 3 Tick 死亡等待
           + 2 Tick 出生保护
           + 从出生点/已知备用落点到当前目标的预计返程
           + 当前目标/资源/任务的机会成本
```

用途：

- 低 HP 时为远处资源冒险，成本会被正确放大；
- 后期一次死亡可能同时丢 D、时间和任务窗口；
- 在“打一下可能死”和“退一步保命”之间做更准确的比较。

**边界**：复活落点不能完全预测，只能用本队初始出生点、已知合法空格和当前感知做不确定性估计，不能当成真值。

### 为什么是新的

现有实现把死亡简化为固定扣分，`respawn_task_route` 只是“复活后改走任务”；这里是把死亡代价放进每个风险动作的估值，属于不同层次。

### 验证

低 HP + 远处资源 + 可见敌人；对比当前保命/贪资源选择；再做全场比赛。不要因为“动作更合理”就当作得分提升。

## 4. 对手资源意图与后期剥夺

### 当前实现

- 资源在本队可见范围内消失、且敌人站在该格时，只记录一个 `recent_competition` 时间戳（`core.cpp:273-281`）；
- 这个信号只被 `early_interception` 使用，而该实验默认关闭（`core.cpp:905-908`）；
- `denial_reward` 只针对公共任务资源，默认关闭（`core.cpp:616-640`）。

### 新思路

把“资源消失”从一次性战斗 cue 升级为**对手资源意图模型**：

- 每次看到本队曾观察到的资源在敌人所在格消失，累加该队的资源价值下界；
- 记录敌人最近移动方向：朝资源区、朝中心堡垒、朝任务点、朝我方；
- 用这些信息估计“谁可能在资源上领先”，进而：
  - 自己落后时，更积极地抢附近高价值资源；
  - 自己领先时，避免无谓交战、优先保 D/任务；
  - 后期对敌人可能拿到的关键资源做**剥夺**，尤其是自己 R≥120 后资源分已封顶、但排名仍比较原始资源价值时。

**限制**：协议只给本队自己的 `score`，没有对手分数。这里只能建立**下界估计**，不能假装知道对手真实分数。所有推断都来自本队可见的资源消失和敌人位置。

### 为什么值得做

当前默认对“对手在收集什么”几乎没有长期记忆；这可能是资源分享/排名的一个新角度。

### 验证

先用现有日志做离线统计：扫描 `observed_resources` 和 `observed_enemies`，统计“资源在敌人位置消失”的频率、涉及的资源价值、发生 Tick；确认信号足够常见，再决定实现。

## 5. 全局分数预算与动态风险

### 当前实现

- 前 1/5 做资源/探索（`core.cpp:533`、`902`）；
- 后 1/3 才提高任务优先级；
- 最后 4 Tick 取消 `damage_reserve`（`core.cpp:1418`）；
- 伤害储备权重 `.054`/D，而实际对抗分边际是 `.03`/D（`core.cpp:1408-1428`）。

### 新思路

做一个轻量的**全局分数预算器**：

```text
resource_gap = max(0, 120 - R)
damage_gap   = max(0, 500 - D)
mission_left = 未完成任务
remaining    = max_ticks - tick
```

根据 gap 和 remaining 决定当前阶段权重：

- 资源 gap 大且时间足：资源/探索优先；
- D gap 大且时间少：战斗优先；
- 任务未完成且临近结束：任务优先；
- 所有 gap 为 0：只做同分价值、防守和低风险收集；
- 动态 `damage_reserve`：不是固定 120，而是按“再死几次会掉下 500 + 剩余时间”计算。

### 为什么是新的

现有大量实验是“改一个标量权重”，这个是把资源/战斗/任务当成三个有上限的目标，显式做预算分配。

### 风险

很容易又变成一组手调权重。建议只引入 3–4 个可解释参数，并严格配对验证。

## 6. 用裁判端做“机制预言机 + 对手联盟”

这是现在最值得做、且**不用改代码**的新思路。

### 6.1 机制预言机

用测试裁判构造小型、确定性的场景，验证规则细节，而不是只看最终分数：

- 洁身自好：本车防御，敌人 20 HP 攻击，确认反伤击杀与 60 奖励；
- 辣椒：踩点、线上 20/80 HP 敌人、保护目标、另一条火线命中自己；
- 天使：点在脚下、点在相邻、点即将过期、已有回血；
- 堡垒 + 爆炸/分裂同 Tick；
- 分裂 + 出生点/备用落点。

这些测试只使用自己的感知和公开事件，不读取全图；目的是确认“规则到底怎么结算”，而不是把测试配置喂给选手。

### 6.2 对手联盟

当前评估主要对默认/防御倾向/内置陪练。可以做一个 **4 种脚本对手的 league**：

- 资源型：`contested_task_resources=true` 或 `competitive_exploration=true`；
- 战斗型：`standoff_fire_risk=true` / `standoff_attack_probe=true`；
- 事件/堡垒型：`event_timing=true` / `fortress_time_budget=true`；
- 探索型：`frontier_lookahead=true` / `information_paths=true`。

用现有 `strategy_eval.py` 的 `--opponents self`、`--candidate-count 1`、`--opponent-param` 就能做，不需要改选手代码。建议 4 图 × 4 席位，至少 16 对/对手，观察候选是否只对“默认对手”有效。

**关键**：把 `--workspace` 指到 `/tmp/rmtc-review`，日志也在 `/tmp`，不碰仓库文件。

示例（路径、域、端口按环境替换）：

```bash
# 在容器内执行
source /opt/ros/humble/setup.bash
source /root/ros2_ws/install/setup.bash

python3 /root/ros2_ws/tools/strategy_eval.py \
  --judge-root /root/rmtc_practice \
  --workspace /tmp/rmtc-review \
  --binary /root/ros2_ws/build/rmtc_bot/contestant \
  --label league-combat \
  --variants default \
  --seats A,B,C,D \
  --opponents self --candidate-count 1 \
  --opponent-param standoff_fire_risk:=true \
  --no-events --domain 91 --port 8591
```

**收益**：这比继续盲调参数更能回答“新策略到底对谁有效”。如果只做一件事，建议先做这个。

## 7. 可选：事件组合与区域拒止

这不是单个事件机制，而是“把事件当作地图控制工具”：

- 世界分裂把地图切成两半时，选择资源更多的一侧，而不是只把它当障碍；
- 辣椒/爆炸用于封锁关键通道或逼迫敌人绕路，即使不拿击杀；
- 堡垒 + 洁身自好：5×5 攻击多个防御目标时的反伤结算；
- 平底锅 + 辣椒：辣椒伤害不吃易伤倍率，需确认；
- 爆炸 + 分裂同 Tick 的死亡顺序和奖励。

其中“用事件做区域拒止”收益不确定，风险较高；建议先做 6.1 的机制验证，再考虑策略化。

### 11.1 新增高优先级不足

#### 11.1.1 同一事件的多个模型几何版本永久共存

**证据**：

- `Events::merge` 只按 `kind + start_tick + rect + points` 去重（`core.cpp:202-205`）；模型“先解错、后修正”时，两版几何都留在 `items`。
- 真实归档中已出现同 `kind/start` 不同 `rect` 的 `unrivaled` 双版本。已核实示例：
  `test-results/fortress-isolated-candidate-known-1792750493554623968/interior779-fortress-long-A/A-1792750494097057537.jsonl`，`start=41` 同时存在 `[[11,8],[15,12]]`（5×5）和 `[[12,9],[14,11]]`（真实 3×3）。
  团队扫描到 14 个文件有同类双版本；另 `v11-reserve-gateway-candidate-*`、`escape-standard-real-*` 也有。
- 代码后果：
  - `environmental_damage` 对 `start==tick` 的每条事件累加（`core.cpp:346-353`）→ 重叠矩形爆炸可能按 2×80 计；
  - `World::effect("unrivaled")` 对任一 rect 连续驻留都返回真（`core.cpp:328-335`）→ 站在错误 5×5 环带也可能获得“无双”；
  - 堡垒目标对两条 rect 全部格出价（`core.cpp:774-797`）；
  - `effect_number` 取最后一条 item 参数（`core.cpp:339-345`），与 `effect()` 的“任一”语义不一致；
  - `Events::context()` 只给最后 32 条（`core.cpp:220-234`），模型容易继续复读旧版本。
- `core_test.cpp:179-185` 目前把“同 kind/start 不同 rect 是新事件”固化成断言，需要重新设计。

**优化**：

- 对 singleton 类（`unrivaled`、`purity`、`world_split`）按“同 kind + 同开始窗口、几何不同”最新版覆盖；保留 `event_revision`/被覆盖日志，只让 Planner 用最新版。
- 对可能合法的多事件（`explosion`、`illusion`）不要无条件覆盖；至少对“重叠且同源修正”的重复解释做 **max/去重**，不要逐条累加致命性。
- `Events::context()` 改为“未结束/未来事件 + 最近少量已结束事件”，避免模型复读。
- 新增冲突日志：`event_conflict`、`superseded_by`、`geometry_revision`。

**验证**：

- 单测：`unrivaled` 5×5→3×3 后 `items==1`、环带不产生 effect、爆炸不双计；
- 离线把归档 `event_memory` 序列回放进 `World`，比较修复前后的目标/动作；
- 500 Tick 默认回归逐字段一致（除新日志字段）。

**边界**：同一 Tick 两个真实独立爆炸不能被误合并；只对 singleton 和无歧义修正覆盖，其他类型保留日志/冲突标记。

#### 11.1.2 洁身自好攻击估值把两个互斥分支相加

**规则依据**：规则 §5.2（一车一动作，先设防御再同时结算）、§8.8（攻击防御中敌人：目标 0 伤害，攻击者受 20 反伤；反伤不吃易伤）。

**当前代码**：

- `incoming` 假设每个可命中敌人都会攻击（`core.cpp:1084-1149`；`standoff_fire_risk` 关闭时 probability=1）；
- `attack` 的 `received` 先取 `incoming*vulnerable`（`core.cpp:1251`），随后又叠加 `defend_probability*reflection`（`core.cpp:1376`）；
- 单敌、purity、hp=25 时，期望被算成 `20 + 0.65*20 = 33`，`death_probability=1`（`core.cpp:1393-1403`），但实际上：
  - 敌人攻击：本车受 20，剩 5；
  - 敌人防御：本车受 0 + 反伤 20，剩 5；
  - 两种都不死。
- 结果是 purity 的 20 Tick 窗口内可能放弃一个可以安全拿到的 60 D 补刀。

**优化**：

- 对每个敌人建立互斥动作分支 `{attack, defend, other}`，复用 `outcomes()`/`robust` 的分布，不要一边按“必攻击”计 incoming，一边又按“防御概率”加反伤；
- 最小修：attack 分支先从 `incoming` 扣掉该目标的攻击贡献，再按 `P(attack)` / `P(defend)` 分别计；
- 保持 `defend` 分支的 purity 反伤奖励（这是 P1-1 的另一方向）。

**验证**：purity 单敌 hp=25/35 不再判必死且能补刀；hp=15 仍优先防御；无 purity 场景逐字段等价。

#### 11.1.3 资源瓶颈在开局高价值资源，不在后期探索

**数据**（P50，949 场）：

- 距 60 满分平均差 **19.72**：资源 **15.87（80.5%）**、任务 2.41（12.2%）、伤害 1.43（7.3%）。
- 资源 120 封顶仅 **30/949（3.2%）**；伤害 500 封顶 **778/949（82.0%）**，其中 777/778 终局仍 D≥500。
- 每场资源增量平均只有 **4.56 次**；资源最后一次增加中位 **Tick 27**，**99.6% 的资源在 Tick100 前入账**，只有 15/949 在 Tick>100 还有资源收益。
- 终局资源 mean 56.5 / median 50；rank1 均资源 **79.62**，rank4 **27.04**。
- **31.5%（299/949）场从未采集任何 20 值高价值资源**；这 299 场全部缺 `collect_high_value` 任务。相反，有 ≥1 次高价值采集的 650 场全部完成该任务。
- 任务失分 65.4% 来自高价值任务；高价值任务完成时刻中位 **Tick 5.5**。

**含义**：

- 当前主要漏分不是“后期不探索”，而是**开局没有拿到高价值资源/没有看到高价值资源**；
- 在 24×24、16 个资源、4 车竞争下，前 30–100 Tick 的资源可见性和路线决定上限；
- 席位差异很大（例如 map62543 A 21.2 vs C 98.8），但样本内、跨批次、对手不同，不能当因果或硬编码席位规则。

**优化**：

- 新增独立实验 `opening_high_value`：前 60 Tick 把“首次高价值资源”作为强机会成本；没有高价值资源可见时，优先最大化新增视野/探索覆盖，而不是后期再补探索权重；
- 高价值资源可见时，在资源奖励/路线中提高优先级；普通资源仍保留，但不因远处普通资源放弃开局高价值窗口；
- 不做“后期探索加权”，数据显示后 100 Tick 资源收益几乎为零；
- 验收用“高价值任务完成率 / 首次高价值 Tick / 资源分达成率”，不要只看总伤害。

#### 11.1.4 辣椒在步骤 6 的死亡会取消步骤 9 的资源/任务收益

**规则依据**：规则 §5.2 步骤 5→6→7→8→9：移动 → 辣椒统一结算死亡 → 扣 60 → 存活车辆收集资源/检查任务；§4.2 同 Tick 阵亡不能收集；§10.1 任务只为存活车辆检查。

**当前代码**：

- `environmental_damage` 只处理爆炸和世界分裂（`core.cpp:346-353`），没有辣椒火线；
- 辣椒只在移动评分里扣 `.08`（`core.cpp:1297-1302`）；
- 到达资源/任务的奖励只在“已经在该格且非 move”时乘 `progress_survival`（`core.cpp:1541-1547`）；“移动进入该格”的 payoff 没有按步骤 6 的死亡折减。

**优化**：

- 把已解析辣椒点纳入终点评估：
  - 自己进入点触发火线；交点免疫，但可能被其他火线命中；
  - 可见敌人在线上时，50 环境伤害（保护免疫、无视防御）；
  - 若预计步骤 6 死亡，资源/任务/到达收益作废，并计死亡成本；
- “已到达”分支也按同一存活条件折减；
- 不猜测谁触发：用保守上界 + 明确日志假设。

**验证**：目标资源格在敌人辣椒线上、进入会死的合成场景应改道或先处理敌人；双车同 Tick 互命中的规则回归；无 pepper 场景逐字段等价。

**与 P1-2 区别**：P1-2 是辣椒进攻/防御的伤害估值；这里是结算顺序导致“步骤 6 死亡 → 步骤 9 收益作废并再扣 60”。

#### 11.1.5 AI 解释时延、串行队列与配额语义

**数据**（P500，36 场、955 次真实调用）：

- accepted **954/955（99.9%）**；模型净耗时 median **1406 ms**（p90 1741，max 4993）；
- 触发 → 解释并入决策的滞后 median **9 Tick**（p90 22，max 111）；
- 78 个首次事件：首次可用提前量 median **3 Tick**；**18/78（23.1%）≤0**（拿到时已生效），25/78（32.1%）≤1；
- 分事件：`unrivaled/fortress` median 16.5 Tick、`illusion` 9.0，可用；`explosion` 2.67、`angel` 2.5、`pan` 0.67、`purity` 0.33、`world_split` -0.17；**`pepper` 6/6 全部迟到，median -4**。

**当前代码**：

- `ai.cpp:55-56/159-192`：单 worker、单 curl handle、FIFO 串行；
- `ai.cpp:128-130`：`timeout=12000ms`、connect=3000ms；
- `ai.cpp:168-186`：最多 3 次尝试；`http_status==0`（含本地读超时）也重试，单条公告最坏可阻塞约 36 s；
- `ai.cpp:73-74`：队列上限 8；`node.cpp:207-217` 每帧逐条提交，且不检查 `submit()` 返回值；
- 协议允许每席位 **2 个在途**，当前未利用。

**优化**：

- 本地读超时（`CURLE_OPERATION_TIMEDOUT`）不要盲目重试；只对连接失败/502/504/429 退避；
- 按 Tick/事件类型设 per-request deadline，而不是所有请求固定 12 s；先本地 fixture 验证；
- 同一感知帧的多条未读公告合批为一次请求（先验证 schema 与事件上下文）；
- 实现最多 2 个在途 worker/handle（协议允许），资格/修复优先；
- `submit` 记录 `queued/dropped/queue_age_ms` 与固定原因码；
- 事件类型预算：只有 `unrivaled/illusion` 等长提前量事件值得复杂时序规划；`pepper/world_split` 在真实模型下太晚，不要为它们再加复杂逻辑。

**验证**：本地慢 HTTP fixture（零费用）模拟 8 条 1.5 s 公告，测排队年龄/首条 lead；离线用现有归档复算 lead 分布；再显式选择真实网关跑 500 ms 压力场。不要放进默认付费测试。

#### 11.1.6 D 封顶后的 239 Tick 低产出区

**数据**（P50，778 场达到 D=500）：

- 封顶 Tick mean 260.7 / median 266；封顶后平均 **239.3 Tick**（median 234，约占整场 47%）；
- 动作结构：封顶后 move 48.6% / **defend 36.0%** / attack 10.4% / wait 4.9%；封顶前 defend 13.1%；
- 封顶后死亡 3036（47.5%），每 100 Tick 死亡率 1.63 vs 1.50；
- 693/778 场出现“死亡把 D 从 ≥500 打到 <500”的 cap_loss 共 2529 次，但 **777/778 终局仍 D≥500**；
- 封顶后攻击且仍有已知资源仅 **44 次** —— “后期贪资源乱打”不成立；真正问题是 **47% 场时没有分数产出**。

**优化**：

- 加入“封顶后状态机”：D≥500+reserve 且仍有未完成任务/资源目标时，优先把时间转成任务/资源/名次剥夺；
- 如果资源已封顶、任务已完成，则转为低风险同分/剥夺策略，而不是继续长时间 defend；
- 不要用“减少死亡/减少攻击”作验收；用封顶后任务完成数、资源、最终名次；
- 规则确认：>500 的原始 D 参与同分比较，不能简单砍掉所有后期攻击。

#### 11.1.7 过期资源记忆污染 `resources.empty()` 门控

**证据**：

#### 11.1.8 复活保护期与重启/重连恢复没有专门状态

**数据**：

- P50：6,394 次死亡，复活间隔恒为 **4 Tick**（6360/6360 有后续存活帧）；非出生点复活仅 11 次（0.17%）；**75.9% 死亡发生在 Tick100–399**，47.3% 发生在 D≥500 后。

**当前代码**：

- `incoming` 在 `f.protected_spawn` 时直接不计算（`core.cpp:1084`）；移动评分没有“离开出生点会失去剩余保护”的代价（`core.cpp:1257-1305`）；
- `Frame` 没有解析 `position_reason`、`respawn_in`、`defending`（`core.cpp:31-41`、`97-155`）；
- `Planner::decide` 在死亡时只返回 wait，`target_` 不清（`core.cpp:374`）；复活后可能继续旧目标；
- `respawn_task_route` 依赖“上一帧 dead + 连续 32 Tick 历史”（`core.cpp:848-882`），漏帧/重启时失效；
- `/referee/event_text` 在首个 perception 前到达会被丢弃（`node.cpp:93-97`），换场/重启没有 pending 重放。

**优化**：

- 加轻量复活状态机：解析 `position_reason`、`respawn_in`、`protected`；死亡/重生时清空 `target_`/恢复任务；2 Tick 保护期内比较“留在出生点/防御”与“离开拿资源/任务”的收益，离开只在收益明显覆盖失去保护时；
- 只使用本队当前感知和已知合法落点，不预测隐藏占位/对手复活点；
- 首帧前公告进入有界 pending 队列，首帧后提交；换场/重启按 session 校验重放；
- 新字段必须可缺省，不能因缺失拒绝整帧。

**验证**：合成 ROS 帧：先 event_text 后 perception；缺失/新增字段；kill/restart 后 retained 公告不重复计费；500 Tick 默认回归逐字段等价（除新日志）。

#### 11.1.9 当前战斗伤害与下一 Tick 事件伤害没有合并

**证据**：

- `event_cost` 使用当前 `hp`（`core.cpp:378-391`），但 action 评分时已经知道本 Tick 的 `received`；
- `move` 分支 `score-=event_cost(end,f.tick+1,false)`（`core.cpp:1296`）；非 move 分支 `event_cost(end,...,f.protected_spawn)`（`core.cpp:1540`）；
- 默认 `event_escape=false`，所以 `escape_damage` 为空；例如 hp=60、本 Tick 受 40、下一 Tick 爆炸 20，`event_cost` 按 hp=60 判断为非致死，可能走进去，实际步骤 4 后只剩 20，步骤 1 的爆炸直接击杀。

**优化**：

- 在 action 评分中对“本 Tick received + 下一 Tick 已知事件伤害”做联合致死检查；或把 `hp-received` 传给 `event_cost`；
- 只对已知事件几何做保守检查，不预测新事件；
- 加合成单测：hp=60、received=40、下一 Tick 爆炸 20，不能进入；不改变非致死场景。

#### 11.1.10 P2 级新增项

- **平底锅易伤默认不计算**：默认只读当前 pan（`core.cpp:1172`），下一 Tick `next_multiplier` 只在 `tactical_forecast` 分支（1476-1489、1526-1528）；普通 move 没有“移动→下一 Tick 双倍伤害”的代价。归档 31 个日志含 pan 事件。建议加 move 分支的期望易伤成本（独立开关）。
- **敌方效果只来自模型 effects**：`World::effect` 对非本队在 illusion 后直接 `continue`（`core.cpp:311-338`）；敌方无双/易伤/回血只能靠模型 effects。可以从本车可见帧推断（无双驻留、pan 成功移动、回血 HP+10），但只用于威胁估值，标 `inferred_effects`，不能当实时真值。
- **未文档化 flag 冲突**：`standoff_robust_trade` 在 `standoff_fire_risk=true` 时被静默禁用（`core.cpp:1244-1249`）；任何“开风险”的消融都会同时关掉默认联合估值。建议 session 日志记录“生效后 flags”，同开时警告/拒绝，补 2×2。
- **感知解析失败整帧丢弃**：任一实体/任务/event_text 超限都 throw（`core.cpp:117-153`），`node.cpp:243-247` 只写 `perception_rejected`，没有固定错误码/动作兜底；归档已有 6 次拒绝。建议加白名单错误码，最小字段可解析时发 wait 兜底（严格不回显原始输入）。
- **E_BLOCKED 审计**：P50 中 35,065 次 `E_BLOCKED`（36.9/场，658/949 场，占 move 12.6%），`invalid=0`；时延 P95 1.24 ms，不是瓶颈。先用 `last_action.error` + 已知障碍/敌人占位离线对齐，确认是合法被占还是规划滞后，再改。
- **decision_type 合规**：规则 §2.3 要求赛前登记枚举、现场只允许 `decision_config.json` 的 `decision_type`；当前无该机制。若准备使用两次合法切换，需要只读加载固定文件、enum→PlannerConfig preset、日志记录；否则正式上场不要用实验 `-p`。

### 11.3 对前文优先级的修正

- **资源优先于伤害**：P50 中伤害分已封顶 82%，资源分差占 80.5%。后续实验应优先“开局高价值资源/资源路线”，不要再把“增加攻击”作为主优化方向。
- **死亡次数不是目标**：6,394 次死亡中 78.8% 发生在 attack 帧，但 v1.1 伤害分损失≈0；真正成本是 4 Tick 停机 + 回程。零死亡场次分数反而更低（26.5 vs 41.2，相关不是因果）。验收应看“死亡后的任务/资源机会成本”，不是死亡次数。
- **`fortress_time_budget` 继续默认关闭**：最新 `fortress-isolated` 4 对中 Δscore 全为 0；`map47297-fortress C` 名次从 2 退到 3；机制确实触发（赛前堡垒目标帧 20→9），但文档中的 +2.5/+29.4 未在“对手不解释事件”的隔离组复现。该增益依赖对手/场次，不能当稳定收益。
- **AI 不是“到了就能用”**：P500 中 26% 新事件在生效后才可用；`pepper` 6/6 迟到。长提前量事件（`unrivaled/illusion`）才值得复杂时序规划；短提前量事件以本地安全为主。
- **P50 的 50 ms/Tick 与正式 500 ms/Tick 不同**：上面资源/死亡/封顶统计来自 P50 无事件；不能直接外推正式比赛，但它揭示了策略结构瓶颈。

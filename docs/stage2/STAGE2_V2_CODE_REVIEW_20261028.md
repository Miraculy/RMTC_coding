# 二阶段 v2 代码分析与优化方向

日期：2026-10-28  
分析版本：`dcd77d8`，与上一发布版本 `ad38286` 比较  
范围：正式入口、二阶段策略与 LLM 代码、既有验收记录、上一轮 DeepSeek 比赛日志

本轮没有构建、运行测试、策略重放、比赛或模型调用，没有修改参赛源码、配置或入口。仅阅读代码、统计已有日志，并整理本文件。文中的历史比赛数据不属于当前版本的新测试结果。

## 1. 总体判断

**v2 有继续作为基线的理由。下一步最值得改进的是机会兑现：更早发现并采到资源、让模型解释及时进入决策，以及让战斗服务于后续得分。**

新版验收记录显示平均名次、前二局数和死亡次数有所改善，但资源没有增加，第二组均分也下降。现有证据支持在已测对手池中保留这一方向，尚不足以证明真实模型事件条件、非中心对称地图和不同对手下均有优势。

建议优先处理两条主线：

1. **工程主线：LLM 排队、429 冷却与失败恢复。**已有真实故障和明确代码机制，影响所有事件能力。
2. **策略主线：资源发现—访问顺序—竞争到达。**同时比较收益和被延迟的机会，比继续提高固定高值奖励更有依据。

无防御版本的战斗机会成本、资源恢复的事件边界和堡垒收益窗口，可以作为后续独立方向。以下建议均未实施，预期收益尚待验证。

## 2. 当前正式程序实际改变了什么

正式二阶段入口仍为：

```text
run_contestant.sh <席位> 2
  → run_stage2_final.sh
  → stage2/install/rmtc_bot/lib/rmtc_bot/contestant
  + stage2/config/final.yaml
```

本次提交只有两项运行策略变化，均位于 `stage2/src/rmtc_bot/src/core.cpp`：

| 变化 | 实际条件与行为 | 主要边界 |
|---|---|---|
| 本象限高值优先 | 第二阶段、有初始出生位置、`tick < 40`、资源价值 `>= 20`，且资源与出生点落在地图相同的横纵半区时，目标奖励增加 `6.0` | 仅作用于已观察或记住的资源；没有按任务是否完成、后续到达时间单独调整该奖励 |
| 移除防御 | 二阶段不再向动作候选添加 `defend` | 所有二阶段局面均生效，包括低血量、特殊事件和比赛末期 |

路径规划、任务奖励、三站资源前瞻、攻击估值、LLM 调度及事件合并逻辑没有随本次提交改变。这两项新行为直接写在代码中，没有新增独立参数开关。

当前决策仍分为两层：先比较资源、任务、探索、事件和敌人相关目标，再比较移动、攻击和等待。因此，选中高值资源不保证每一步都向其推进；防御动作消失也不证明所有无进展僵局消失。

主要代码位置：

- [资源奖励与竞争折扣](../../stage2/src/rmtc_bot/src/core.cpp)：约 750–832 行。
- [三站前瞻](../../stage2/src/rmtc_bot/src/core.cpp)：约 834–897 行。
- [动作候选及局部评分](../../stage2/src/rmtc_bot/src/core.cpp)：约 1592–1937 行。

## 4. 资源方向：从目标加分走向完整短路线

### 4.1 高值奖励覆盖不到“没发现”和“发现时已太晚”

本轮只读统计上一轮 16 份正式车日志：在原有观察轨迹中，**11/16 局在前 40 Tick 看见过本象限高值资源**，另外五局没有满足这条新奖励的观察条件。

这不是新版策略重放，也不是新版收益上限。新版行动变化会改变后续观察；这个统计只用于说明新奖励的直接作用范围。

两个旧版案例能区分不同损失原因：

- **S02-A：发现后已经立即追，仍被抢走。**Tick 15 首次看见 `(7,7)` 的高值资源，同 Tick 就设为目标；Tick 23 对手位于该格，资源已经消失。此处应研究发现时机、此前访问顺序和绕行成本，单独提高同一目标的价值未必改变结果。
- **S02-C：整场没有看见高值资源。**这类缺口依赖探索方向与路线带来的视野，已知资源加分无法直接处理。

原始证据：[S02-A 本车日志](../../test-results/stage2-release-ad38286-deepseek-20261027/matches/S02-A/A/A-1793098159668014011.jsonl)、[S02-C 本车日志](../../test-results/stage2-release-ad38286-deepseek-20261027/matches/S02-C/C/C-1793098160093899852.jsonl)。

### 4.2 当前加分与前瞻之间存在需要统一的估值条件

20R 对应 5 分资源分，而新增奖励为 6，属于较强偏好。它在高值任务完成后仍存在；当实际资源分接近封顶时，也没有随剩余资源分空间同步减少。

“本象限”按地图中线划分，不能反映障碍绕行和可见对手的到达优势。中心对称、资源公平都不能保证本象限资源一定由本车更早取得。

三站前瞻复用了当前奖励。后续站点没有按到达时刻重算 40 Tick 条件；正式配置下，竞争折扣也没有随每一站的到达时间重新计算。如果加分意图是尽早取得资源，这种估值方式与滚动执行之间可能产生偏差。它是静态代码中可见的设计取舍，尚未证明已造成某一局退步。

### 4.3 建议方案

保留现有最多三站的搜索框架，统一比较以下短路线：先高值再普通、先普通再高值，以及经过一个观测点后再采集。

每站共同考虑：实际资源分增量、未完成任务增量、预计到达时刻、已知通路与未知路段、可见竞争者的到达可能性、途中观察机会，以及延迟其他资源的代价。第二、三站应按累计到达时间更新竞争估值，避免反复使用当前状态下的奖励。

保留普通资源链尤其重要。历史更广泛的高值优先实验曾使平均资源从 50 降至 44.375，出现为了探索而放弃可兑现普通资源的反例。新版条件更窄，不能直接等同于旧实验，但仍应防范相同损失机制。见 [资源分阶段实验](../research/RESOURCE_PHASE_REVIEW_20261024.md)。

## 5. LLM 方向：提高解释的及时性和故障恢复能力

### 5.1 已有问题证据

上一轮 64 车次中，HTTP 往返中位数约 1.56 秒，而请求快照到返回的逻辑时间差中位数为 8 秒、P95 为 17 秒。正式车 128 次事件机会中，112 次曾获得完整匹配解释，35 次在生效前获得完整匹配解释。

“完整匹配”采用时间、几何及关键参数的严格口径，不等于只有 35 次事件产生作用；曾匹配也不保证后续不存在冲突版本。这些结果说明 HTTP 成功率不足以代表事件能力可用性。

S04-A 的真实故障更明确：一次 12 秒超时后出现 124 次 429，最终达到 180 次尝试上限，后续模型调用停止。429 来自本地代理的同席位并发限制，不能直接归为 DeepSeek 官方限流。

证据：[AI 审计](../../test-results/stage2-release-ad38286-deepseek-20261027/ai-audit.json)、[S04-A 本车日志](../../test-results/stage2-release-ad38286-deepseek-20261027/matches/S04-A/A/A-1793098682500077344.jsonl)。

### 5.2 代码中的对应机制

- 公告入队时保存 `tick` 与 `known_events`；等待期间不会刷新任务上下文。
- 普通公告主要按入队顺序处理，新公告仅优先于资格请求和结构修复请求。
- HTTP 429 若不附带识别范围内的错误码，会记为 `http_error`，未进入针对限流错误的同任务退避分支。
- 失败后会撤销公告去重，后续感知可再次提交该公告；总尝试达到成功预算两倍后，整场请求停止。

这些机制位于 [ai.cpp](../../stage2/src/rmtc_bot/src/ai.cpp) 的 `submit`、`request` 和 `run`，本次更新没有修改。

### 5.3 建议方案

优先按 HTTP 状态识别 429，增加客户端与公告层面的冷却，避免同一故障快速消耗尝试预算。发送前刷新已确认事件上下文，同时保留公告原始观察时间；在已有语义身份依据时，合并重复更新或降低其队列占用。

事件语义仍由 LLM 解释，不能用本地字符串规则猜事件内容，也不能按公告年龄一律删除可能仍影响当前状态的消息。

另一个小范围方向是矩形端点规范化：101 次结构拒绝中有 87 次属于端点顺序问题。如果协议中的矩形仅表示轴对齐两角，可以研究在校验层规范化顺序，减少为同一几何事实再次调用模型。缺失几何和时间等信息仍须拒绝或修复，不能猜测补齐。

## 6. 战斗方向：为无防御版本补齐后续机会成本

旧版 16 局中，有 10 局出现至少 20 Tick 的同格连续防御且资源、伤害、任务均无增长，3 局存在至少 100 Tick 的此类区间。取消防御有现实动机，但这些区间不能全部视为可安全追回的收益。

当前实现将防御从所有二阶段状态删除。战斗先于移动结算，低血量车辆即使选择移动，也可能在移动执行前死亡。代码虽然计算死亡惩罚，部分移动和驻留收益仍未按存活分支扣除，因为正式配置中的 `survival_conditioned_progress` 为 false。

建议研究短期行动比较：当前攻击、移动或等待之后，本车还能否兑现资源、任务和事件机会；若阵亡，会损失多少时间和机会。在保持当前不防御约束时，可优先改善更早脱离火线、取消无法执行的移动收益，以及降低伤害已封顶后的高机会成本交战。

若后续允许重新讨论防御，可研究有明确期限和退出条件的少数例外。任何例外都需要避免重新形成原先的长期僵持，不能直接恢复旧全局逻辑。

现有 `safe_progress_moves`、`survival_conditioned_progress` 等机制有无收益或退步记录，不应直接组合启用。局部安全不等于整段路线可兑现，见 [低血量推进与下一 Tick 火线](../research/DYNAMIC_FIRE_REVIEW.md)。

此外，本次将多处“必须 defend”断言改为“不得 defend”。例如 `PurityDefenseAvoidsLethalAttackAndReflection` 现在只验证动作不是防御，已经不再验证其名称所表达的避开致死攻击和反伤。**这不证明新版策略错误，但测试通过不能继续承载原来同样的战术保证。**后续应验证替代动作的效果、可接受损失及退出行为。见 [核心测试](../../stage2/src/rmtc_bot/test/core_test.cpp) 约 468 行及 1391 行。

## 7. 两个范围较小的具体问题

### 7.1 资源受阻恢复被整份事件历史限制

`resource_blocked_recovery` 要求事件列表和效果列表都为空。事件历史保留到换场，因此一旦收到事件解释，即使事件已经结束、地点与当前路线无关，该恢复机制仍会停用。

上一轮启动次数为零，说明实际覆盖有限，但不能把零触发全部归因于这一条件。更合理的方向是检查当前及近期事件是否影响备选路径，而不是通过删除历史来满足空列表条件。历史记录仍可能用于重建持续效果。

代码位置：[core.cpp](../../stage2/src/rmtc_bot/src/core.cpp) 约 455 行、1469 行。

### 7.2 堡垒奖励需要对齐首次可用时刻

局部驻留奖励仍可能奖励“本 Tick 刚满足驻留，但下 Tick 已经无法使用效果”的行动。应统一首次可用 Tick、事件结束 Tick 和比赛结束 Tick，再计算奖励。

这是可单独处理的边界问题，不等于应直接开启此前未证明有效的整套事件时间规划。代码位置：[core.cpp](../../stage2/src/rmtc_bot/src/core.cpp) 约 1745–1755 行；历史分析见 [v1.2 几何核验](STAGE2_V12_GEOMETRY_REVIEW_20261026.md)。

## 8. 地图先验与状态边界

用户补充的条件是：二阶段大部分地图中心对称、资源基本公平，但存在非中心对称地图；一阶段与二阶段地图不同，不同场次地图也不同。

中心对称和公平性适合用作当场探索的软先验，再由本车实际观测修正。它们不能直接推出隐藏资源坐标、剩余资源配额或本车一定先到。出生象限只是粗略几何偏好，更有价值的判断依据是已知通路和可见竞争形成的到达优势。

继续保留按 session 清空地图、资源、敌人和事件记忆的逻辑；不继承一阶段地图，也不复用其他场次地图。当前 [World::update](../../stage2/src/rmtc_bot/src/core.cpp) 约 297–300 行已执行换场清空。

## 9. 建议优先级与后续判断标准

| 优先级 | 方向 | 问题证据 | 未来应观察的结果 |
|---|---|---|---|
| 高 | LLM 队列、429 冷却和失败恢复 | 真实故障、历史时延及明确代码路径 | 正确解释提前到达比例、队列滞后、故障后恢复；不只看 HTTP 成功率 |
| 高 | 资源发现与短路线兑现 | 未发现、已追但赶不上、普通资源链丢失 | 最终资源份额、高值任务完成率、总分和名次，以及严重退步 |
| 中 | 无防御版本的交战机会成本 | 旧防御僵持、战斗先于移动、局部收益未完全按存活计价 | 任务兑现、死亡损失、无收益停滞和最终排名 |
| 中 | 受阻恢复的事件边界 | 任意事件历史导致机制停用 | 有效覆盖、备选资源实际取得及事件风险 |
| 中 | 堡垒首次可用时间 | 局部奖励窗口边界 | 奖励是否对应实际可用效果与收益 |

后续每个方案应保留当前版本作为明确对照，分别评价，不把多个开关的单项历史收益直接相加。资源和排名是不同目标；平均总分上涨不能替代资源份额或排名改善。

目前没有足够依据继续提高固定 `+6`、统一延长开局窗口，或一次打开多个旧实验开关。本文件只提出分析与方向，没有启动后续实施或验证。
